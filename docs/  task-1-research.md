# Задание 1. Исследование моделей и инфраструктуры

## Контекст задачи

QuantumForge Software имеет распределённую корпоративную базу знаний: Markdown/MDX-файлы в репозиториях, Confluence, PDF-спецификации, Google Docs, Zendesk Guide и другую документацию.

Основная проблема — сотрудники тратят много времени на поиск актуальной информации, документация дублируется, устаревает и не имеет единого жизненного цикла.

Цель RAG-бота — сократить время поиска, повысить точность ответов, снизить нагрузку на тимлидов и поддержку, а также выявлять пробелы в документации.

## Сравнение LLM-моделей

| Критерий | Локальные Hugging Face модели | OpenAI | YandexGPT |
|---|---|---|---|
| Качество ответов | Зависит от выбранной модели. Малые модели хуже следуют инструкциям, крупные требуют GPU | Высокое качество, хорошее следование инструкциям | Хорошее качество для русскоязычных сценариев |
| Скорость работы | На CPU медленно, на GPU приемлемо | Высокая скорость через API | Высокая скорость через API |
| Стоимость | Нет платы за токены, но нужна инфраструктура | Оплата за использование API | Оплата за использование API |
| Развёртывание | Сложнее: нужны GPU, память, настройка inference | Самое простое: API-ключ и HTTP-запросы | Простое при наличии аккаунта в Yandex Cloud |
| Конфиденциальность | Максимальный контроль, данные не уходят наружу | Нужно учитывать передачу данных во внешний API | Нужно учитывать передачу данных во внешний API |

### Вывод по LLM

Для MVP лучше использовать облачную LLM, потому что она быстрее внедряется, не требует GPU и даёт более стабильное качество ответов.

Для production-сценария компании лучше рассмотреть гибридный подход:

- обычные внутренние документы можно обрабатывать через облачную LLM;
- конфиденциальные документы и документы аудита лучше обрабатывать локально или через private deployment;
- в ответах обязательно указывать источники;
- при недостатке контекста бот должен отвечать: «Я не знаю».


## Сравнение моделей эмбеддингов

| Критерий | Sentence-Transformers | OpenAI Embeddings |
|---|---|---|
| Скорость создания индекса | Средняя на CPU, хорошая на GPU | Высокая, так как расчёт выполняется на стороне API |
| Качество поиска | Хорошее для базового RAG, особенно при подборе подходящей multilingual-модели | Обычно высокое качество semantic search |
| Стоимость | Бесплатно, но используются ресурсы сервера | Оплата за API |
| Конфиденциальность | Документы остаются внутри инфраструктуры | Тексты отправляются во внешний API |
| Простота внедрения | Нужно установить модель и зависимости | Достаточно API-ключа |

### Вывод по эмбеддингам

Для учебного проекта и MVP выбираю Sentence-Transformers, потому что это бесплатный и локальный вариант. Он позволяет создать индекс без передачи корпоративных документов во внешний сервис.

Для production можно рассмотреть OpenAI Embeddings или другой managed embedding API, если требования безопасности позволяют отправлять текстовые фрагменты во внешний сервис.

## Сравнение FAISS и ChromaDB

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Скорость поиска | Очень высокая | Хорошая |
| Скорость индексации | Высокая | Хорошая, но есть больше служебной логики |
| Сложность внедрения | Низкая | Средняя |
| Хранение metadata | Ограниченное, часть логики нужно реализовывать самостоятельно | Удобная работа с коллекциями и metadata |
| Поддержка фильтрации | Ограниченная | Лучше подходит для фильтрации по metadata |
| Эксплуатация | Простая для локального прототипа | Удобнее для более продуктового решения |
| Стоимость | Бесплатно, минимум инфраструктуры | Бесплатно self-hosted, но требует больше поддержки |

### Вывод по векторной базе

Для учебного проекта выбираю FAISS, потому что он проще, быстрее запускается и подходит для локального прототипа.

Для production-сценария с ролями пользователей, фильтрацией по источникам, владельцам документов, типам документов и датам обновления лучше рассмотреть ChromaDB или другую полноценную vector database.
